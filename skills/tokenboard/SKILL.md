# TokenBoard

Use the bundled scripts to install TokenBoard collection on the user's machine. Never print upload tokens. Never upload prompts, completions, file contents, or raw conversation logs.

## Install

When the user provides a pairing code, run:

```bash
TOKENBOARD_CODEX_BATCH_SIZE=200 node scripts/setup.mjs --pairing-code <pairing-code> --base-url <tokenboard-base-url>
```

Optional flags:

```bash
--base-url https://tokenboard.example.com
--timezone <iana-timezone>
--device-name "Codex Desktop"
--schedule-times 09:00,12:00,18:00,23:00
--skip-collector
--skip-schedule
--skip-hook
--skip-initial-sync
--repo-url https://github.com/evepupil/TokenBoard.git
--repo-ref <branch-or-ref>
--package-manager pnpm|bun|npm
--client git|binary
--use-device-link
```

`--client binary` installs the released Go client instead of a git checkout. The
default is `git`, and every existing install stays on it; the choice is stored as
`clientType` in the config and can be changed back at any time. A binary install
downloads one release tarball into `~/.tokenboard/bin/tokenboard` and needs no
Node.js, no checkout and no `pnpm install` afterwards. It is the smaller install
and the one that cannot get stuck on a dirty checkout, but its upgrade channel is
the release feed rather than the repository branch. Do not switch an install to
`binary` unless the user asks for it or the release feed is confirmed to be the
intended source for that machine.

> **The binary channel has no published release as of 2026-10-23.** The client
> is still under development and validation, so `v0.1.0` was turned back into a
> draft. `--to-binary` and `self-update` against the default feed both fail
> closed in that state (`self-update` exits 1 with "release lookup did not land
> on a tag page"), which is the intended behaviour rather than a bug — there is
> simply nothing to install. Keep installs on `git` until a release is published
> again.

To roll an install back from `binary` to `git`, do not hand-edit the config
file: with `activeServer`/`servers` present, `clientType` is profile-scoped and a
root-level edit is silently overridden on read. Use the config helper instead
(`mergeConfig({ clientType: 'git' })`), which updates the root and the active
profile together.

After setup, report whether config was written, schedule was installed, and initial sync succeeded. Do not show `uploadToken`.

New clients store credentials by TokenBoard server origin under `servers` and mirror the active profile to the legacy top-level `endpoint`, `uploadToken`, `deviceId`, `installationId`, and `timezone` fields. Re-running setup for a private or official server should update only that server profile while preserving credentials for other TokenBoard servers.

When the server returns an install claim, setup writes `~/.tokenboard/device-link.json` with mode `0600`. Treat this file as sensitive local recovery state. Never print, copy, upload, or paste its `installClaim`; status output only reports whether the file exists.

If config is missing but `device-link.json` is still present, setup can explicitly request a reconnect pairing code with `--use-device-link` or `TOKENBOARD_USE_DEVICE_LINK=1`. This sends only `deviceId`, `installationId`, and the install claim to `/api/v1/device/reconnect-pairing-codes`; a successful exchange invalidates the old install claim, and failure must stop setup instead of silently creating a new logical device.

When the Web UI rotates an upload token, it shows the new token once together with macOS/Linux/Git Bash and Windows PowerShell `rotate-token.mjs` commands. Run the platform-matching command on the matching client machine to update only the matching server profile in `config.json` and refresh `device-link.json`. Do not paste the rotated token or install claim into chat logs, screenshots, docs, or unrelated terminals. If the command says the server profile is missing, stop and reconnect the device instead of creating an ad hoc config.

Install prompts generated by the TokenBoard web app include `--timezone` from the browser's
detected IANA timezone unless the user edits the form. If the flag is omitted, `setup.mjs` falls
back to the local Node.js `Intl.DateTimeFormat().resolvedOptions().timeZone` value.

The setup script clones or updates `https://github.com/evepupil/TokenBoard.git` into `~/.tokenboard/TokenBoard`, bootstraps workspace dependencies with `corepack pnpm install --frozen-lockfile`, uses the collector dependency on local `ccusage`, writes or updates the active server profile in local config, installs the daily schedule and notifier hooks unless skipped, and runs a full-history initial sync unless skipped. Do not change the initial sync to a 7-day window unless the user explicitly asks. Codex history is processed in batches during full scans; use `TOKENBOARD_CODEX_BATCH_SIZE=200` by default, lower it only when the user needs lower peak resource usage. Each temporary Codex scope accepts at most 4 GiB for one session file and 4 GiB total for one batch. A larger JSONL file is handled by a bounded streaming metadata projection that retains only session/model and token metadata; the projected output remains subject to the batch limit. Oversized rows without usage or subagent metadata may be skipped with a warning, while malformed input, unknown oversized record types, oversized usage rows, and projection output over the batch limit fail explicitly. `--package-manager` controls fallback provider invocation when the local `ccusage` binary is unavailable; use `--repo-url`, `TOKENBOARD_REPO_URL`, `--repo-ref`, `TOKENBOARD_REPO_REF`, `--package-manager bun`, `--package-manager npm`, or `TOKENBOARD_PACKAGE_MANAGER=pnpm|bun|npm` only when the local environment requires a non-default collector source, branch, or package manager. If a web install prompt includes `--repo-ref` or `--branch`, preserve it so the collector stays on the server-selected ref.

For diagnosing Codex hook collection cost without exposing session paths, set `TOKENBOARD_COLLECTOR_DIAGNOSTICS=1`. The collector then reports canonical attribution cache hits/misses and the number of files in a narrowed canonical scan; unset the variable for the default quiet behavior.

When setup uses `--skip-initial-sync`, or an explicit bounded `--since` value other than `all`, it warms hook cursors before installing hooks. This keeps the first hook event from doing the historical backfill that the user skipped or bounded. A full-history initial sync does not need cursor warming.

Notifier hooks are recommended but optional. Use `--skip-hook` only when the user does not want setup
to change Codex or Claude Code config during initial install. To install hooks later, run:

```bash
node ~/.tokenboard/TokenBoard/skills/tokenboard/scripts/install-hook.mjs --source all
```

Default `--source all` installs Codex and Claude Code hooks only. Use `--source codex` or `--source claude-code` for a single notifier integration. Antigravity CLI status line capture is a separate explicit opt-in because it updates the visible agy status line command:

```bash
node ~/.tokenboard/TokenBoard/skills/tokenboard/scripts/install-hook.mjs --source antigravity-cli
```

Antigravity collection has three source values: `antigravity-cli`, `antigravity`, and `antigravity-ide`. Scheduled or manual `--source all` syncs read available local Antigravity history metadata for all three products. Antigravity CLI token totals are derived only from `~/.gemini/antigravity-cli/conversations/*.db` `gen_metadata.data`. Its optional `statusLine.command` handler writes a bounded sanitized local diagnostic log, but that log is not collector input and never affects uploaded snapshots. Standalone Antigravity and Antigravity IDE read SQLite metadata when present and use a bounded local language-server metadata projection for `.pb`-only histories. Direct `.pb` decoding remains out of scope.

OpenCode, Pi, Grok Build and DeepSeek Harness are collected from each tool's own local usage records: `opencode` reads `~/.local/share/opencode/opencode.db`, `pi` reads `~/.pi/agent/sessions`, `grok-build` reads `~/.grok/{sessions,archived_sessions}`, and `deepseek-harness` reads `~/.dsh/sessions`. These four install no notifier hook and are not part of hook-mode syncs; a scheduled or manual `--source all` sync reads them when the tool is installed and skips it when it is not. Only token counts, model ids and timestamps are read — never prompts, replies or local paths. Grok Build and DeepSeek Harness report no cost, so their usage uploads `costUsd: 0` and every surface labels the cost as unavailable.

The status line handler reads bounded stdin, writes sanitized local JSONL, and never uploads or starts sync from the foreground status line process. Antigravity history collectors must only persist or upload token counts, model, timestamp, source, cost placeholder, and dedupe hashes. They must not persist or upload prompt text, completion text, cwd, workspace, email, plan_tier, tool arguments, file paths, raw conversation IDs, or raw history blobs. The status line JSONL still contains stable hashed conversation IDs, so treat `~/.tokenboard/antigravity-cli-statusline.jsonl` as a private local state file. Do not parse Antigravity logs, `/credits`, or `/usage` as TokenBoard upload sources. Antigravity cost is unavailable for all three sources; snapshots use `costUsd: 0` and UI/report output must label that cost as unavailable.

The default schedule is `09:00,12:00,18:00,23:00`. When the user asks for custom times, require `HH:MM` 24-hour values and pass them through `--schedule-times`. The scheduler target is platform-specific:

- macOS: `~/Library/LaunchAgents/com.tokenboard.daily-sync.plist`
- Linux: `~/.config/systemd/user/tokenboard-daily-sync.timer`
- Windows: one `TokenBoardDailySyncHHMM` scheduled task per configured time

The installed schedule runs `sync.mjs --mode sync --scheduled`; the sync resolves its source at run time from the config `source` field (default `all`), so editing that field retargets scheduled syncs without reinstalling the schedule.

If the user pasted a TokenBoard install prompt from the website, follow the prompt and run the included setup command. Treat pairing codes as short-lived secrets and do not repeat them unless needed to execute setup.

## Sync

Daily and manual sync default to a 7-day lookback window. `--since` accepts `YYYYMMDD` or
`YYYY-MM-DD` for every source. Use `--since all` only when the user explicitly asks for a
full-history backfill.

After upgrading a collector with a large Antigravity CLI SQLite history but no completed full-history
baseline, a bounded Antigravity CLI scan fails explicitly rather than report a partial or incomplete result.
Run one `node scripts/sync.mjs --mode sync --source antigravity-cli --since all` after confirmation;
do not delete the existing cursor or configuration to bypass that check.

Sync runs a lightweight upgrade first by default. It updates the local collector checkout and this installed skill from the configured TokenBoard repo, then continues with collection. Hook syncs do not run this upgrade path; they only enqueue and reconcile usage. The GitHub ZIP archive fallback runs only when the collector directory is missing or not a git repository — a standard git checkout whose fetch fails reports the git error and stops, it never re-clones over the worktree. If upgrade still fails, treat it as a warning unless sync itself fails. For troubleshooting only, skip the upgrade with `--skip-upgrade`, `TOKENBOARD_SKIP_UPGRADE=1`, or `TOKENBOARD_AUTO_UPGRADE=0`.

A `clientType: binary` install upgrades differently: the sync runs the Go client's own `tokenboard self-update`, which downloads the latest release, verifies it against the release's `checksums.txt`, and swaps it in only after the new binary has answered `version`. The git checkout is not involved and may stay dirty or absent. To move an existing git-clone install onto this channel, run `node scripts/upgrade.mjs --to-binary` — it installs the current release and flips `clientType`, keeping the checkout as the rollback (set `clientType` back to `git`). The release feed and the git default branch are published from different places, so migration is explicit opt-in, never a default.

To move one source at a time, add a `perSource` map to the config instead of flipping `clientType`: `{"perSource": {"pi": "go", "codex": "ts"}}` runs `pi` on the released binary and leaves `codex` on the checkout. Entries accept `go`/`binary` and `ts`/`git`. A named `--source` follows its own entry; an unmapped source keeps the machine-wide `clientType`. An `all` run collects everything with a single client, so it refuses a map that disagrees with `clientType` rather than silently running one client for both — sync each source separately while the map is mixed, and clear it once everything has moved. `status.mjs` prints the map as written.

An existing Git collector checkout with tracked or untracked changes, or one whose status cannot be read, stops the upgrade before any fetch or checkout. This deliberate stop does not try the ZIP archive fallback; resolve or preserve the local worktree first.

Before moving any source onto the binary client, compare the two implementations on this machine's own data:

```bash
node scripts/shadow-dual-run.mjs --until <yesterday>
```

It runs `tokenboard shadow` for every source the machine has, appends one JSON line per source to `~/.tokenboard/logs/shadow-dual-run.jsonl`, and exits nonzero only on a real difference or failure. It uploads nothing, installs no schedule, and never touches the real cursors. A source reported as `not-installed` simply is not on this machine; `busy` means a concurrent sync held the collector lock and the comparison was skipped. `empty` means both sides agreed on zero snapshots — a source whose data falls entirely outside the window logs it every day, and it is not coverage; rerun that source with `--since all` to actually compare it. Pass `--until <yesterday>` so the day still being written is out of scope — two sequential scans of a live session legitimately differ on the current day. `--summary` prints how the last records actually went (pass `--limit N` to widen) without paying for a fresh comparison; `status.mjs` reports the same window as its `shadowDualRun` block, so the daily health check already carries the trend.

For legacy multi-profile Codex configuration, `CODEX_HOME` remains a comma-separated list. If a single home path itself contains a comma, use the unambiguous `TOKENBOARD_CODEX_HOMES_JSON` environment variable with a non-empty JSON array of paths instead; do not put that path in `CODEX_HOME`.

Do not run `upgrade.mjs` from notifier hooks. Hook-triggered syncs pass `--hook` to `sync.mjs`; this is the supported boundary that disables auto-upgrade during Codex or Claude Code session-end events. Antigravity CLI status line capture does not trigger hook sync; scheduled or manual sync reads local Antigravity history metadata.

Scheduled, manual, preview, and hook collection share one local sync lock. The coordinator holds that
lock while its hook child collects, so the child must not try to acquire it again. Signals that arrive
during a running hook are retained and handled by one cooldown-delayed trailing run rather than
starting repeated immediate reconciliations.

The hook-only cooldown defaults to 15 minutes to avoid repeatedly reconciling a large active Codex
history. Set `TOKENBOARD_NOTIFY_COOLDOWN_MS` to an integer number of milliseconds from `60000`
through `7200000` to tune the maximum delay after the most recent successful TokenBoard reconciliation when
no shared sync lock is contended; hook hosts cannot inject that env var reliably, so the same
range can be configured durably as the `notifyCooldownMs` key in the TokenBoard config file
(env wins when both are set). The hook handler persists its signal before the background notifier
validates this setting; shared lock timeouts still schedule a one-minute retry.

A hook trigger that lands within half an hour of a scheduled sync time is skipped. The schedule
times come from the config file's `scheduleTimes` (what `setup.mjs --schedule-times` writes) or
`TOKENBOARD_SCHEDULE_TIMES`, and are compared in the machine's local time because launchd, systemd
and the Windows task scheduler all fire on local wall-clock time. The scheduled run scans
`config.source` — `all` by default — so it collects the same usage the skipped hook would have; the
skipped trigger's signal stays queued for the next hook run to acknowledge.

When a scheduled sync cannot acquire that lock within its timeout, it writes a private deferred
retry state under the TokenBoard config directory and performs a bounded in-process retry. The retry
attempts only lock contention, makes at most five attempts with a one-minute delay after each
continued lock contention, skips checkout upgrade, and stops immediately on a collector error.
`status.mjs` exposes the retry phase and attempt count without printing local paths or error details.

`notify.cjs` coalesces pending work by source and starts at most one detached dispatcher while an
existing dispatcher or cooldown trailing process is alive. The legacy signal file is used only when
atomic queueing fails, and that failure remains visible. For verified append-only Claude Code and
Codex JSONL files, hook cursors read only the appended suffix and reconcile only the newly affected
dates; legacy cursors without the file hash or trailing-newline marker, truncation, or replacement use the
full-file path.

Bounded Antigravity syncs retry up to 30 older pending daily-model groups per run. A successful
upload acknowledges only the groups included in that upload, so an interrupted or partial run does
not discard older local usage.

After acknowledgement, Antigravity CLI retains recent SQLite event identities for incremental
reconciliation and compacts older identities behind a persisted frontier. If a bounded scan finds an
unknown SQLite event at or before that frontier, it stops and requires `--since all`; it never
silently adds the event to a compacted total. `--since all` rebuilds canonical daily-model snapshots
from SQLite rather than adding a local aggregate. This preserves idempotent collection without raw
conversation identifiers or unbounded cursor state.

Preview without upload:

```bash
node scripts/sync.mjs --mode preview --source all
```

Upload:

```bash
node scripts/sync.mjs --mode sync --source all
node scripts/sync.mjs --mode sync --source all --since all
```

Manual upgrade without syncing:

```bash
node scripts/upgrade.mjs
```

If a Codex session file disappears between scan and copy, the collector should warn on stderr and
continue with the remaining session files. Treat non-ENOENT copy failures, provider command
failures, or upload failures as real failures that need debugging.
Missing Antigravity local history is optional in `--source all` syncs. Malformed installed Antigravity history metadata is a real failure that must be debugged instead of silently discarded. The optional status line log remains private local diagnostic state and is not parsed by the collector. In hook mode, real parse or validation failures should fail fast while unavailable Antigravity products remain optional.

## Status

Check local config and installed schedule metadata:

```bash
node scripts/status.mjs
```

The JSON output includes configuration-presence flags, `clientType` (`git` or `binary`), `packageManager`, `scheduleTimes`, device-link presence, and hook status, including `antigravityCli`. It must not print upload tokens, install claims, device identifiers, endpoints, or local paths.

When the dual-run log exists it also reports a `shadowDualRun` block: the last 50 records condensed into per-outcome counts (`match`, `empty`, `diff`, `notInstalled`, `busy`, `error`), the span they cover, and `lastDiffAt`/`lastErrorAt` when present. It is the same window `shadow-dual-run.mjs --summary` prints, read through the harness's own summarizer, and it carries counts and timestamps only — record messages can hold client error text with local paths, which status never prints. The block is omitted when no comparison has run.

For a `clientType: binary` install it also reports a `client` block: whether the client and the bundled ccusage are present on disk, and their versions. A missing file or a version that does not match what the client expects is the signal that the install is not what the config claims; `status.mjs` reports the versions but does not print the paths they live at.

Notifier hooks use `~/.tokenboard/bin/notify.cjs` and only enqueue a background sync signal. They must not run `ccusage`, scan files, or upload in the foreground hook process. On Windows, every process spawned by the notifier must set `windowsHide: true` so hook execution does not open a console window.

Antigravity status line capture uses `skills/tokenboard/scripts/antigravity-statusline.mjs` and writes `~/.tokenboard/antigravity-cli-statusline.jsonl`. It must not use `~/.tokenboard/bin/notify.cjs`.

Hook sync sets `TOKENBOARD_HOOK_MODE=1`. In that mode the collector uses local cursor files in
`~/.tokenboard` to parse only new or changed Codex and Claude session JSONL files. Upload failures
leave cursor entries pending so the next hook can retry. The parser only identifies affected
usage dates; uploaded snapshots are still produced by a narrow `ccusage` reconciliation window for
those dates.

Codex session roots may be symbolic links when the target is explicitly configured. Set
`TOKENBOARD_CODEX_SYMLINK_ROOTS_JSON` to a JSON array of approved real directories, for example
`["/Volumes/Work/CodexArchive/archived_sessions"]`. The collector resolves only `sessions` or
`archived_sessions` root links whose target is inside one of these directories; nested directory or
file links remain rejected. Setup persists this value with
`--codex-symlink-roots-json '["/path/to/approved/archive"]'`. Missing, malformed, or out-of-bound
targets fail the sync with a diagnostic instead of falling back to unrestricted traversal.

Scheduled runs write private `scheduled-sync-state.json` (or a source-suffixed state file for a
non-`all` source) next to the config. `status.mjs` reports only its source, lifecycle status,
timestamps and exit code; private error details remain local.

## Uninstall

Remove only the daily schedule by default:

```bash
node scripts/uninstall.mjs
```

Remove the local config file and installed notifier hooks, while keeping the collector checkout and `device-link.json`:

```bash
node scripts/uninstall.mjs --remove-config
```

This keeps the installed binaries as well: a `clientType: binary` install leaves `bin/tokenboard` and the bundled `bin/ccusage` in place, because only the config file and the hooks are named for removal. Use `--remove-config-dir` to take the whole config directory (and with it the binaries) away.

```bash
node scripts/uninstall.mjs --remove-config-dir
```

Remove the schedule, notifier hooks, collector checkout, local config, and `device-link.json` when the user asks for a full uninstall:

```bash
node scripts/uninstall.mjs --all
```

Scheduled runs write logs to `~/.tokenboard/logs/daily-sync.out.log` and `~/.tokenboard/logs/daily-sync.err.log`. Rotated logs are capped at 1 MiB and kept for 7 days.

## Troubleshooting

- If Node is missing or older than 22.23.4 (22.x) / 24.22.1 (24.x), ask the user to upgrade Node.js — the setup, sync, and collector install scripts refuse to run on older releases because they carry known TLS and decompression vulnerabilities.
- If the collector cannot reach the configured TokenBoard base URL, ask the user to configure proxy environment variables or verify the TokenBoard custom domain.
- If pairing fails, ask the user to generate a new pairing code from TokenBoard.
