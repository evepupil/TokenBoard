  `2026-11-10-hot-cursor-incremental.md` §6 共同记下的最后一项空白——此前的热 cursor 验证

### 1.1 已知边界：已确认 + 尺寸与 mtime 都不变的重写不会被发现

同一组夹具上，把 cursor 条目的 `pendingUpload` 手工置为 `false`（模拟上传成功 acknowledge 之后的稳态；
`preview` 本身不上传，所以只能这样构造），再把文件做等长改写（`10-07 → 10-06`）并用
`touch -r` 把 mtime 原样恢复：

| 指标 | 热跑                               | 全新冷扫                    |
| ---- | ---------------------------------- | --------------------------- |
| 日期 | 只剩未改动文件的行（`2026-10-25`） | `2026-10-06` + `2026-10-25` |

被改写文件的 `(size, mtime)` 与 cursor 记录完全一致，`skipByMetadata`（`scan.go:431`）直接跳过，
新内容不会被读。这是**两侧共有的**短路——TS 的 `session-cursor.ts:346` 用同一个 `sameMetadata` 谓词。
触发它需要「改写后 mtime 回到原值」，正常文件写入不会这样（写入本身就会刷新 mtime）；因此记为边界而非缺陷，
与 TS 语义保持一致。未确认（pending）的条目不受影响：pending 会绕过该短路并走全摘要，上面的实验里
pending 状态下同样的等长改写是被发现的。

### 2.1 日期平移夹具的失败机制（2026-11-12 复核）

事件日期早于路径日期、且窗口整段落在路径日期之前时，TS 与 Go 都产不出快照：

| 运行（`--since 20261107 --until 20261107`，事件全为 11-07，路径 `sessions/2026/11/08/…`） | 结果                                                                                              |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Go plain preview，UTC                                                                     | 2 行，11-07                                                                                       |
| Go plain preview，Asia/Shanghai                                                           | 0 行（rc 0）                                                                                      |
| Go hook，UTC                                                                              | 2 行                                                                                              |
| Go hook，Asia/Shanghai                                                                    | **rc 1**：`Codex hook reconciliation returned no snapshots for parsed usage keys: 2026-11-07/all` |
| TS plain preview，UTC                                                                     | 2 行，11-07（与 Go 逐字段一致）                                                                   |
| TS plain preview，Asia/Shanghai                                                           | 0 行                                                                                              |
| TS hook，Asia/Shanghai                                                                    | **rc 1**，同一文案                                                                                |

机制在 `internal/collect/adapters/codex/paths.go:306-354`（`CodexFileEligibility`，移植自
`paths.rs:165-182`）：`--until` 的边界只比较**路径日期**（`untilPathDate` = `--until` 次日当地午夜换算到
UTC 的日期，UTC 下即 `--until` 本身），窗口内的 mtime 不参与。于是 +08 时 `--until 20261107` 只保留路径日期
≤ `11-07` 的文件，路径是 `11/08` 的文件在源头被剪掉，报告无行。UTC 时上界是 `11-08`，文件保留，
而事件按自身时间戳归到 11-07，正常产出。该规则本身已被 `TestUntilPathDateIsUtcDateOfNextLocalMidnight`
（`paths_test.go:276`）钉住，且两侧逐位一致——**不是移植缺陷**。

真正值得记录的是后果：hook 的窗口来自变更日期（`hookDateBounds`，two sides same），若某个变更文件的
所有事件都早于路径日期、且时区在 UTC 以东把上界压到路径日期之下，hook 会对账失败并整源报错。真实 codex
日志里路径日期通常等于或早于首个事件日期（文件在会话开始当天创建），日常不会触发；触发需要路径日期与
内容日期错位（例如夹具平移，或手工移动/恢复文件）。hook 失败走的是 fail-closed 并重试一次，不静默丢数据。

## 3. 结论

- claude-code 与 codex 的 hook 增量在**文件缩小**与**整体重写**（含同尺寸、含前缀变化）下，
  热跑产出的绝对状态都与同一磁盘状态的全新冷扫逐键、逐字段一致；被删掉的行对应的键不再出现在输出中。
- 唯一未覆盖的残余是「已确认条目 + 尺寸与 mtime 同时不变」的重写，需要刻意伪造 mtime，且 TS 侧同样如此（§1.1）。
- 至此 `go-client-spec.md` §6 记下的热 cursor 空白（追加、缩小、整体重写）全部有实测证据；
  平台侧的证据见 `2026-11-11-windows-linux-verification.md`。
- GUI 两源的 language-server 路由仍只有单测（见 2026-11-10 文档 §5.2），那也是另一个独立条目，不属于本项。
